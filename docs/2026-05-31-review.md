## High Priority

### H1: `console.*` instead of `hilog`

**Files:** `EntryAbility.ets`, `ShareIntent.ets`, `Index.ets` — 20+ occurrences

HarmonyOS recommends `hilog` for structured logging with domain/tag filtering. `console.*` output is harder to filter in production logs and doesn't support log levels.

```typescript
// Current (19 occurrences)
console.info('Index aboutToAppear');

// Recommended
import hilog from '@ohos.hilog';
const DOMAIN = 0x0001;
const TAG = 'Folio';
hilog.info(DOMAIN, TAG, 'Index aboutToAppear');
```

### H2: Token stored in plain `@State` — visible in component tree

**File:** `Index.ets:71`, `SettingsPanelComponent.ets:35`

The auth token is a `@State` field passed as `@Prop` to child components. In ArkUI, `@State` values are observable and may be logged in debug tools. For sensitive data:

- Use `@StorageLink` with encrypted preferences (`@ohos.data.preferences` with `SECURE`)
- Or keep the token only in the service layer, never in UI state

### H3: `@Prop` callback pattern — runtime crash risk

**Files:** All components with `@Prop callbacks: *Callbacks`

The `@Prop` decorator does not support function types. While the current code wraps callbacks in objects (post-crash fix), any future developer adding a bare function `@Prop` will get a runtime crash. Consider:

- Adding a lint rule or code comment at the top of each component file
- Documenting this constraint in CONTRIBUTING.md

## Medium Priority

### M1: `console.info` in `EntryAbility.ets` logs full want parameters

**File:** `EntryAbility.ets:10,23`

```typescript
console.info(`...params=${JSON.stringify(want.parameters ?? {})}`);
```

This logs all launch parameters, which may include sensitive data from other apps sharing content. Filter to only log known-safe keys.

### M2: 52 catch blocks — inconsistent error handling

Some catch blocks log errors, some show toasts, some are empty. The `formatError` improvement (commit `66ba59f`) helps, but consider a unified error handler pattern:

```typescript
private handleError(context: string, error: Object): void {
  const msg = this.formatError(error);
  console.error(`[Folio] ${context}: ${msg}`);
  this.setNotice(msg, true);
}
```

### M3: `for` loops with index — 41 occurrences

Many loops use `for (let i = 0; i < arr.length; i++)` instead of `for...of` or `forEach`. This is fine for performance but harder to read. Not a bug, but technical debt.

### M4: No input validation on URL/title fields

**Files:** `AddLinkOverlayComponent.ets`, `EditLinkOverlayComponent.ets`

TextInput values are passed directly to the API without sanitization. While the Linkwarden API should handle this, client-side validation (URL format, max length) improves UX.

### M5: `searchDebounceTimer` type is `number` but `setTimeout` returns `TimeoutId`

**File:** `Index.ets:181`

ArkUI's `setTimeout` returns a `TimeoutId` type, not `number`. Using `number` works but may cause type issues in future SDK versions.

## Low Priority

### L1: Duplicate `CollectionPickerTrigger` builder pattern

The collection picker trigger UI is defined inline in `AddLinkOverlayComponent` and `EditLinkOverlayComponent`. Could be extracted as a shared `@Builder` or small component.

### L2: Magic numbers for HTTP timeout (30s) and debounce (300ms)

**Files:** `LinkwardenApi.ets:433-434`, `Index.ets`

Extract as named constants:
```typescript
const HTTP_TIMEOUT_MS = 30_000;
const SEARCH_DEBOUNCE_MS = 300;
```

### L3: `CollectionMatchHints` builder is unused

**File:** `Index.ets` — dead code from a previous iteration. Should be removed.

### L4: No `aboutToDisappear` cleanup in component files

Extracted components don't have lifecycle cleanup. If they ever start timers or listeners, this will leak. Not an issue currently but worth noting.

## Architecture Notes

**Strengths:**
- Clean 4-layer architecture (common/services/pages/components)
- Pure-JS mirror pattern for testability (tooling/)
- BookmarkService facade pattern for online/offline switching
- 266 tests covering core business logic
- Good i18n support (zh_CN + en_US)

**Areas for growth:**
- No dependency injection — services are instantiated directly
- No state management pattern (e.g., AppStorage for shared state)
- Components rely on callback objects instead of events
